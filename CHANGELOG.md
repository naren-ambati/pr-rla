# Changelog

Every release of `pr-rla` and `pr-rla-mcp`, newest first. The two packages are released together with one version ([`docs/compatibility.md`](docs/compatibility.md), versioning). Below 1.0, a change to the CLI, an output or a record is a minor version and is listed here. Adding a field is compatible; renaming or removing one is listed here.

## 0.1.0: unreleased

Nothing is published yet: no npm package, no public repository, no tag. This entry describes what the first public release carries: all eleven units of the phase 3–4 design on top of the phase 1–2 audit. The release steps are [`docs/release-checklist.md`](docs/release-checklist.md). Licence: decided by the founder before release.

### The audit (phases 1 and 2)

- **Claim D**, a ballot-polling risk-limiting audit (Wald's SPRT, as in BRAVO) over the changes that landed on a default branch in a window with no recorded human review: `init`, `register`, `freeze`, `sample`, `record`, `status`, `verify`, `simulate` ([`docs/concepts.md`](docs/concepts.md), [`docs/statistics.md`](docs/statistics.md)).
- The population is every change that landed on the default branch: merged pull requests and direct pushes, with no commit counted twice under merge-commit, squash, rebase or fast-forward merges.
- Built-in providers `github` (and GitHub Enterprise Server), `gitlab` (and self-managed), `bitbucket-cloud`, `bitbucket-data-center` and `json-file`; an external Gitea/Forgejo plugin as the worked example ([`docs/writing-a-provider.md`](docs/writing-a-provider.md)).
- The provider SDK (`pr-rla/provider`), the ledger SDK (`pr-rla/ledger`) and the conformance kits (`pr-rla/testing`), at `providerApiVersion` 1 and `ledgerApiVersion` 1.

### Added in phases 3 and 4

- **Trusted time (U1).** RFC 3161 tokens over each signed record's SHA-256 from k = 2 of the registered timestamp authorities, by operator; eight authorities bundled, four on by default (Sigstore, DigiCert, GlobalSign, Microsoft); offline verification with pkijs and asn1js; record schema v2; `register` and `freeze` exit 5 with too few tokens. A Rekor v2 client, tested against mock logs only ([`docs/trusted-time.md`](docs/trusted-time.md)).
- **The fetch broker (U2a).** Every outbound request through one path: a host allowlist, a read-only guard, credential placeholders swapped only on approved https origins, a per-host rate governor whose defaults are the smallest published limits, timeouts by destination, the one retrier, and a scrubbing recorder.
- **Issue-tracker ledgers (U4).** `github-issues` and `gitlab-issues` (GitHub Enterprise Server and GitLab self-managed through `base_url`), verdicts read from label-event history; the ledger conformance kit; the Jira example ledger; time-stamped ledger checkpoints, hash-chained, pushed across clones with `checkpoint --push` (never forced).
- **The plugin lock and the isolated plugin host (U2b).** `pr-rla.lock.json`, written only by `plugin add` and `plugin lock`; external plugins out of process under Node's permission model; `trust: full` as an opt-in; `--plugins builtin-only`; `plugin check`; local consent for every credential grant and for `trust: full` (`plugin approve`).
- **SDK carry-overs (U3).** `selector.bots`, the pinned history head, `Actor.id`, `reviewGranularity`, `landedVia` with `direct_push_via_merge`, `populationOptions`, and `pr-rla/http` under its own `HTTP_HELPER_VERSION` 1.
- **The audit API and the MCP server (U5).** Every command is a formatter over `src/api`; the read-only subpath `pr-rla/api/read`; `pr-rla draw-context <n>`; the separate `pr-rla-mcp` package, eight read-only tools over stdio ([`packages/pr-rla-mcp`](packages/pr-rla-mcp)).
- **CI integrations (U7).** A GitHub composite action with its own lockfile, a GitLab CI/CD component and plain snippet, and a Bitbucket Pipelines step, all tested on fixtures and mock servers ([`docs/ci/`](docs/ci/README.md)).
- **Assistant integrations (U6).** A Claude Code plugin (the MCP server, the `review-draw` skill, a guard hook), and Codex and Cursor setup ([`docs/assistants/`](docs/assistants/README.md)).
- **Org-pooled audits (U8).** One registration, freeze and certificate for a list or a rule of repositories; a resumable, all-or-nothing freeze; `freeze --dry-run --estimate` ([`docs/org-pooled-audits.md`](docs/org-pooled-audits.md)).
- **Per-verdict signatures (U9).** A git-file verdict signed on its own with `record --sign` (an SSHSIG over `pr-rla-verdict/v2` bytes that name the registration, the manifest and the seed); provenance `self-asserted`, `account` or `presence`; a registered minimum enforced by check 7. `presence` is printed as `presence (user-presence flag verified; key hardware not attested)` and has been tested with software keys only.
- **Docs and release engineering (U10).** The doc set and its index ([`docs/README.md`](docs/README.md)), the compatibility table, `SECURITY.md` with a placeholder contact, `CONTRIBUTING.md`, this changelog, the release checklist, a doc check (`npm run docs:check`: dated output blocks, offline links, CLI commands and flags, exit codes), a secret grep over both tarballs (`npm run secret-grep`), and a build that starts from an empty `dist/`.

### Exit codes

0 success · 1 a check failed, a refusal or a usage error · 2 ESCALATE, R not yet published, or an assistant hook block · 3 population below the registered minimum · 4 stopped before finishing (run the printed command again) · 5 a record written without enough timestamps · 6 INCOMPLETE. Codes 0–3 keep their phase 1–2 meaning; 4, 5 and 6 are new in this release ([`docs/compatibility.md`](docs/compatibility.md)).

### Behaviour settled during the build

Nothing was released before 0.1.0, so no released audit is affected. Audits made with a pre-release checkout (test fixtures, and any trial audit) meet these rules:

- **Draws are bound to the registration** for schema-v2 audits: draw *i* = SHA-256(randomness ‖ registrationSha256 ‖ uint64be(*i*)) mod N, so freezing again cannot move a draw. v1 audits keep the manifest's hash.
- **`verify` exits like the certificate of a VERIFIED audit** (2026-11-12, found in the live sandbox showcase): 2 when the sequential test escalated, 3 when the population is below the registered minimum, as `status` does. It exited 0 there before, so the GitHub Action, the GitLab component and the Bitbucket step passed a `verify` job on an audit whose reviews had found too many failures.
- **The record hints of an audit that counts signed verdicts only name `--sign`** (2026-11-13, sandbox showcase): `sample` and `draw-context` said `--reviewer <you>`, which writes a line such an audit ignores.
- **Unproven is not certified.** A time that k operators do not prove, a check that was skipped and a population that could not be rebuilt make `verify` INCOMPLETE (exit 6). `status` withholds the certificate (`target reached · CERTIFICATE WITHHELD (why)`) for an unproven time, for verdicts it could not read, and where its own gate shows check 7 would FAIL. `verify --offline` is never VERIFIED.
- **A review counts as a human decision** only if it is an APPROVED or CHANGES_REQUESTED review by a non-bot account that is not the author, submitted at or before the merge.
- **Verdict signatures are over `pr-rla-verdict/v2`**; a line signed over v1 bytes, a git-file line's own `provenance`, and a commit's signature count for nothing.
- **A git-file audit verifies from a full clone**, at the path its registration records (`ledgerPath`); a shallow, grafted or partial clone FAILs check 7.
- **Check 7 FAILs when the ledger it loads is not the registered one**; a registration names its signing key inside its signed bytes (`publicKeyPem`).
- **A lock's credential grants and `trust: full` need the local approval** of whoever runs the command (`pr-rla plugin approve`, or `plugin add`/`plugin lock`); without it the credential is withheld and a `trust: full` plugin is refused.

- **An audit runs only the plugins its signed registration names**, at every command: `freeze` refuses another provider, `draws`, `draw-context`, `sample`, `record`, `status` and `checkpoint` bind the registered provider and ledger before they open them, and `verify` FAILs check 5 or 7 on any difference (name, source, integrity, trust, options hash; an external plugin's version too) without running the swapped plugin. A built-in's version is shown, not compared.
- **`verify`, `status` and `freeze --dry-run` run on a read-only context**, for the person who runs them: a ledger's request that is not a read is refused before it is sent, and their approvals and `--accept-lock-grants` still apply.
- **The draw → issue mapping is bound by a time-stamped publication record.** When a ledger publishes draws, `sample` signs the index it leaves and has the registered authorities time-stamp it, in `audit/<window>/ledger-publication.json` (`pr-rla/ledger-publication/v1`). Check 7 FAILs a verdict read from an issue no proven publication lists, an index that is not an append-only extension of the latest one, and issue numbers out of draw order; a publication short of tokens makes `sample` exit 5 and check 7 INCOMPLETE. `foreignIssues` is no longer an index field (the test-only ledger option `foreign_issues`, which check 7 FAILs). The GitHub ledger names an issue by its numeric `id`, and the Jira example checks its option ids and its summary marker.
- **One check-7 gate** (`check7Gate`) is run by `verify` and by `status`, so `status` withholds the certificate (`verify check 7 would FAIL: …`) wherever `verify` would FAIL. A checkpoint covers the last counted verdict only when its tokens are proven.
- **A review whose time is unknown is no human decision** (`Review.timeUnknown`: GitLab, Bitbucket Data Center and Bitbucket Cloud cases); the change stays in the population.
- **Text from outside pr-rla is fenced in every read result.** An SCM's or tracker's response, a plugin's or ledger's answer, a reviewer or note: in `pr-rla/api/read` and the MCP server each line says pr-rla's words and points to `untrusted.errors[i]`; the CLI quotes it in place, escaped. Identifiers are checked where they enter instead.
- **A hostile plugin cannot take the plugin host or the MCP server down**: answers go through a `reply()` that never throws, echoes and log lines are cut to 2 KiB, a request id that is not a whole number stops the host, and the MCP server fails only the call a stray rejection came from.
- **Bounded estimates and retry hints.** An `estimateRequests` figure must be a whole number of requests within a bound, or the estimate prints no figures; the replay reserves in at most 1,000 batches; a retry hint that is not a finite number is dropped (`RETRY_HINT_INVALID` from the broker). In read-only mode the broker scrubs every secret of 8 characters or more the caller holds out of each response.
- **Draws cannot be steered by a name.** The population is ordered by a draw key (the SCM's repo id for a rule pool, the registered path for a repo or a list, then `#n` or `@sha`; `contracts.md` §5), so renaming or respelling a repository between freezes moves no draw, and check 2 FAILs a manifest that spells a registered repo or list entry another way. A single repo's order, and so its draws, are unchanged.
- **A selector's logins are bound to account ids** at `register` (`ScmProvider.resolveAccounts`) and signed into the registration; selection, freeze, status and verify match them by id only. A prospective registration whose provider cannot resolve them is refused; a retrospective one warns.
- **A labels stratum reads labels at landing**, from label history (`labelHistory`, `labelsAt: "landing"`); a provider without it is refused at `register`, and an older registration is INCOMPLETE. A rule repo that matches now, is not in the pool and was not registered makes check 5 INCOMPLETE.
- **One offline verify core.** `status` runs verify's checks 1, 2, 3, 4 and 6 (and the check-7 gate) on the same records, so it never shows CERTIFIED where `verify` would FAIL: each FAIL is a FAILED withholding (exit 1, `offlineFails` in `--json`). A schema-v1 audit's check 6 is INCOMPLETE, and a v2 registration without `publicKeyPem` FAILs check 1. A FAIL shown from local evidence (the ledger index, the checkpoint file, the registered identity) stays a FAIL when the ledger's reads were refused for want of a credential.
- **`verify --registration <sha256>`, `status --registration` and `status --log-key`.** Pin the registration's SHA-256 you were handed before R published (prospective: before the window opened), and the transparency logs you trust; a status of a frozen audit below the minimum reports the refusal, exit 3.

### Final fix round (changes to outputs)

- **Only `verify` prints CERTIFIED.** `status`, `audit_list` and the MCP `status` tool never rebuild the population (check 5), so a target the sequential test has reached now reads `target reached · CERTIFICATE WITHHELD (population not verified: run \`pr-rla verify\`)`, `certified` is false, and `status` exits 6 (1 where a check would FAIL). The Action's `state` output is `WITHHELD` for it; `CERTIFIED` comes from an online `verify`.
- **Check 3 compares the registration's proven time with R.** A registration whose tokens prove it existed only after round R was public now FAILs check 3, and the verifier holds its own clock tolerance and default accuracy (600 s and 60 s): a record that states other values FAILs checks 1 and 2, and a checkpoint or publication stamped under them is not proven.
- **`status` with the tracker not read** (`audit_list`, the MCP default) runs the offline core too, carries `offlineChecks` and `offlineFails`, and exits 1 on what verify would FAIL.
- **A next-page link on another origin is refused** by the GitHub, GitLab, Bitbucket and issue-ledger clients before anything is sent (the credential rides on every request they make).
- **A plugin call that asks the host for nothing for `CALL_IDLE_TIMEOUT_MS` (270 s) while it keeps sending heartbeats is stopped** (`PLUGIN_HOST_TIMEOUT`).
- **The CI install pins what was installed.** The GitLab component and snippet and the Bitbucket step install into their tool directory first, with their own empty npm config and an explicit `--registry`, then compare `PRRLA_INTEGRITY` with the integrity npm recorded for the installed package. An empty pin means "not pinned": set it.
- **The Claude Code guard** blocks a glob that can match a protected file or the approvals file, whether or not the file exists yet (`verdicts.jso?l`, `appr?vals.json`, `~/.config/pr-r?a/approvals.json`, `~/.config/pr-rla/*`).
