# Independent review: pr-rla phases 3–4 refined design

**Verdict: not ready to build from as written, but close.** The founder's decisions (D1–D10, the answers file) are applied consistently, the dependency graph is acyclic and the build order is a valid topological order of it. The statistics, seed and seven checks are untouched. The problems are in the seams between units. The design assumes an `AuditApi` layer that does not exist in the code yet. It leaves SDK fields without an owner and retries in two places. It contradicts an approved requirement on clock skew. It promises a read-only property its package layout cannot give. None of these needs a redesign. Each needs a decision written down before bolt 1 or bolt 2 starts. Checked against `BUILD-NOTES.md`: `src/api`, `src/net`, `src/plugins` and `src/timestamp` do not exist, and every command in `src/commands/` still does its own I/O.

## What holds up well

- The dependency graph is acyclic, and the founder's build order satisfies every edge. The U1-before-U2a case is handled with a broker-contract adapter.
- The founder's decisions D3, D7 and D8 and the answers are applied consistently, with a kept/changed/added record in every file.
- Fewer-than-k handling, `0 of k` and exit 5 are specified end to end with testable cases.
- Read-only MCP state, with job and cache limits and a core-built untrusted-content fence, is a sound, checkable design.
- The Node 25 network-denial limit, the software-key presence limit (T16) and the unverified list are stated honestly. Each has a named test that settles it.
- All 71 FR IDs are mapped to units, and the FR5.5 estimate bound is concrete and testable.
