# Security model

This page states what pr-rla protects and what it does not. It covers external plugins (threat T6 in `docs/design/phase-3-4/nfr-design.md`) and trusted time (T17); the other parts of the model are added as their units land.

## External plugins (T6)

A provider or ledger plugin is code you did not write. It decides the population, and anything it can read or send, it can steal. The npm worms of 2025–2026 (Shai-Hulud, chalk/debug, ChainDrop) took tokens from the environment and from `~/.npmrc`, at run time, from packages with valid provenance. So pr-rla treats every external plugin as untrusted unless you say otherwise.

### What pr-rla does

1. **Nothing external runs until you lock it.** `pr-rla plugin add <use>` resolves the plugin from `.pr-rla.yml`, loads it in the host (below, never in pr-rla's own process), and prints everything it is about to trust: source, version, `resolved`, the npm integrity from `package-lock.json`, a `treeSha256` over every installed file of the plugin and of each runtime dependency, its trust, its hosts, write paths and credentials. Only after you confirm (or pass `--yes`) does it write `pr-rla.lock.json`, and record your approval on this machine (item 9). Nothing else writes that file: `register` with an unlocked external plugin exits 1 and tells you to run `plugin add`. A dependency must have an npm package name (`name` or `@scope/name`) and sit in a `node_modules` directory, not around the audit directory, or resolution refuses it before anything is hashed, granted or run (`plugin check` too); so a `package.json` cannot widen a plugin's read grant to the audit repo.
2. **Every load re-checks the lock.** npm checks integrity only at install. pr-rla re-resolves the plugin and re-hashes its files at every load, and refuses on any difference: `plugin … changed since it was locked (treeSha256 …); run "pr-rla plugin lock …" after reviewing the change`. A symlink that leaves the plugin's tree aborts the hash. A path plugin must live inside the audit repo, so a third-party verifier loads the same files. The registration records the plugin's name, source, version, tree hash, options hash and trust, and `verify` warns when the plugin it loads is not the registered one.
3. **It runs out of process by default** (`trust: isolated`), in a child Node process started with:
   - `--permission`, with read access to the plugin's own files and its dependencies' only (never their `node_modules` or `.git`), plus pr-rla's child script and SDK modules;
   - no permission to write files, start processes or workers, load addons or use WASI;
   - no `--allow-net`, so on Node 25 or later the child has no network at all;
   - an environment of `PR_RLA_HOST=1` and placeholders only: a locked credential that is set, and that you approved (item 9), reaches the plugin as `prrla-cred:<ENV>`, never as its value. One you did not approve does not reach it at all.

   A credential's hosts are locked like everything else. A self-hosted server's credential can follow the URL option its definition names (`hostFromOption: "base_url"`; the Gitea and Jira examples do): pr-rla, not the plugin, takes the host from that option, only from an `https:` URL, and records it in the lock entry, so the reviewer sees it at `plugin add` and a changed option is refused at load. The registration's options hash covers the option.

   A ledger still cannot write files. Its local index (`LedgerContext.index`, `audit/<window>/ledger-index.json`) travels over IPC, and pr-rla reads and writes that one file for it, atomically; nothing else on disk is reachable. `register`, `record` and `verify` read an isolated ledger's provenance and hosts through the host (or from its lock entry), never by importing it.
4. **Every request goes through the parent's fetch broker** over IPC (`pr-rla/ipc/v2`), including a plugin's own `fetch()`. The broker allows only the locked hosts and keeps providers read-only on the wire. It swaps a placeholder for the secret only:
   - on `https:`, for the exact origin granted (host and port; the default port normalised), and on no hop after a redirect from https to http;
   - in `authorization`, or a header the plugin declares for that credential (`headers: ["private-token"]`); anywhere else the request is refused unsent (CREDENTIAL_HEADER_NOT_ALLOWED);
   - `prrla-basic:<USER_ENV>:<TOKEN_ENV>` becomes Basic auth the same way.

   Anything else is refused unsent. "Read-only" covers what a server may treat as a write: a GraphQL document, `operationName` or `extensions` in the URL, and `X-HTTP-Method-Override` (and its kind) count. A secret a server echoes back, raw, percent-encoded or base64 (also as a JSON encoder escapes any of these inside a string), in the body, a header, the status text, a redirect's URL or an error, is replaced with its placeholder before the plugin sees the response; the recorder scrubs the same forms. A credential the plugin declares `secret: false` (an identity, such as a Basic username) is left alone, so a participant list that names you still reads right, and it is sent only as the user part of `prrla-basic:`. Waits run on the command's clock in the parent, only while a call is in flight, for at most 15 minutes, and end when the host closes; fetches are served only while a call is in flight, at most 64 at once.
5. **The host watches the child.** A call sends a heartbeat every 10 s; 60 s of silence after the child reported ready stops it (start-up has its own 60 s limit), and the command fails with the plugin's last output lines and writes nothing. Messages travel as length-prefixed frames on a pipe, and one over 64 MiB is refused from its first four bytes, before any of it is buffered. Results are re-validated by the core whatever the child returns.
6. **`trust: full` is an explicit opt-in** (`plugin add --trust full`): the plugin runs in pr-rla's process with your environment and files, as plugins did before. It loads only with your approval on this machine (item 9), only when every `pr-rla` it can resolve is the one running it (the tree hash leaves pr-rla out), and the imports its modules make on pr-rla's thread may resolve only inside its hashed files and declared dependencies (never their unhashed `node_modules` or `.git`) and the running pr-rla's own `dist`, `src`, `node_modules` and `package.json`. Every command that loads it prints `PLUGIN TRUST: full (<name>@<version> runs with your environment and files)`, the registration records it, and `verify` repeats it.
7. **`--plugins builtin-only`** (or `PR_RLA_PLUGINS=builtin-only`) refuses every external plugin before anything resolves or imports it. Any other value is refused, so a typo never lets external code in.
8. **`pr-rla plugin check <use>`** reports the lock status, `npm audit signatures` for a package plugin, the hosts and credentials the plugin asks for, and runs the conformance kit (the provider kit, or the ledger kit for a ledger) through the host on the plugin's own recorded fixtures. Its last line is always `conformance = correctness, not safety: a malicious plugin can pass it`.
9. **The lock is the repo's; what it lets a plugin send is yours.** A repo's `pr-rla.lock.json` still pins what a plugin is (source, integrity, tree hash) and what it may read. Two things in it take effect only with the consent of the person running the command, recorded in a per-user file outside every repo (`$PR_RLA_APPROVALS_FILE`, else `$XDG_CONFIG_HOME/pr-rla/approvals.json`, else `~/.config/pr-rla/approvals.json`, written atomically and readable by you only):
   - a credential grant (a placeholder swapped for one of your secrets, sent to an origin);
   - `trust: full`.

   An approval is for the plugin as locked: its use, its `treeSha256`, its trust, its exact grants (each env var, the https origins, any declared headers, `secret: false`) and its write paths. Any change needs a new one. `plugin add` and `plugin lock` record it, since locking a plugin is consenting to it; for a plugin someone else locked, `pr-rla plugin approve <use>` shows exactly what it grants and records it (`--yes` without a terminal). Without an approval, an isolated plugin's credentials are withheld (it runs as if they were unset, a placeholder written into its code is refused with CREDENTIAL_NOT_APPROVED, and one line names `pr-rla plugin approve <use>`), and a `trust: full` plugin refuses to load. The built-in providers and ledgers follow the same rule for the token their options point at (`token_env`, `base_url`): their own service's defaults are approved already (GITHUB_TOKEN and GH_TOKEN to https://api.github.com, GITLAB_TOKEN to https://gitlab.com, BITBUCKET_TOKEN and BITBUCKET_USERNAME to https://api.bitbucket.org); any other variable or origin is withheld until you approve it (`pr-rla plugin approve <use>` in the audit repo, or `pr-rla plugin approve --env GHE_TOKEN --origin https://ghe.example.com`), and an `http:` origin never gets one. The one escape is `--accept-lock-grants` (or `PR_RLA_ACCEPT_LOCK_GRANTS=1`): it accepts the repo's grants and trust for that run, records nothing, and is only for a repo you control, such as your own CI.

### If you verify someone else's audit

`pr-rla verify` runs the audit's plugins on your machine. What protects you, without any approval:
- **Your tokens stay yours.** The auditee's lock cannot send your GITHUB_TOKEN, AWS keys or any other variable anywhere: a plugin you have not approved gets no credential, not even a placeholder, and a built-in pointed at another host (a `base_url`, a `token_env`) sends nothing it was not already allowed to (your GitHub token to api.github.com and the like). Public audits verify anonymously.
- **Nothing runs in your process.** A `trust: full` plugin is refused until you approve it; an isolated one runs in the host, under the permission model, without your environment.
- **It reads only its own files.** Its dependencies must be installed packages; none can widen what it reads to the audit repo or your home directory.
- **Only the registered plugins run (P1).** `verify` reads the configured provider's and ledger's identity from their definitions or lock entries before running anything, and runs only the plugins the registration names (name, source, files, trust, every option). A `.pr-rla.yml` that points at another provider or ledger, even another built-in, is a FAIL of check 5 or 7, and that plugin never runs, so nothing is sent to its hosts.
- **Nothing writes while it is read (P1).** `verify`, `status` and `freeze --dry-run` run on a read-only broker: a ledger's non-read request is refused before it is sent, even under the write paths it declared, and with a token you approved.

What it does not protect you from: an isolated plugin still runs the auditee's code in a child process, and on Node 22 and 24 that child can open its own sockets and send out what the SCM returns to it (anonymously, unless you approved a token). Verify on Node 25 or later, and approve a token only for a plugin you have reviewed, for the narrowest token you have.

### What isolation guarantees

Tested with `test/fixtures/plugins/hostile`, a plugin that tries each of these (`test/plugin-host.test.ts`; `node scripts/demo-plugin-host.mjs` prints the results):

| Node | Token theft through the environment | Reading `~/.npmrc`, gh config, other files | Sending out repo data the plugin sees | Writing files, starting processes |
|---|---|---|---|---|
| 22 and 24 | prevented: it reads a placeholder | blocked by the fs-read scope (*a seatbelt*) | **possible**: Node 22 and 24 have no network control, so the plugin can open its own sockets | blocked (*a seatbelt*) |
| 25 or later | prevented | blocked (*a seatbelt*) | blocked: no `--allow-net` (*a seatbelt*) | blocked (*a seatbelt*) |

Measured on 2026-11-03 with Node 22.23.2, 24.20.0 and 26.8.2 on macOS. Node 25 itself was not available; the Node 25-or-later row rests on Node 26.8.2, where IPC works under `--permission` without `--allow-net` and the plugin's socket is refused with `ERR_ACCESS_DENIED`.

### The limits, stated plainly

- **On Node 22 and 24 a malicious plugin can still send repo data out.** It cannot read your tokens, but it sees whatever the SCM returns to it (private repo data included) and can open a socket to anywhere. Run pr-rla on Node 25 or later to close that.
- **The permission model is a seatbelt, not a security boundary.** Node's documentation says it "does not protect against malicious code" and that malicious code can bypass it; CVE-2025-55130 was a symlink bypass of the fs flags on Node 20, 22, 24 and 25. On Linux, `/proc/<ppid>/environ` is readable by the same user; it is outside the fs-read scope, which is again a seatbelt.
- **A placeholder protects the secret, not the request.** The plugin can still make any read request the token allows to the hosts it is locked to. Give it the narrowest token you have: read-only, one repository.
- **A plugin decides the population.** Isolation does not stop a provider from dropping changes; `verify` rebuilds the population with the provider it is given. Review a plugin before you lock it, and lock the same version your auditor will use.
- **An approval of `trust: full` pins what the plugin imports, not what it chooses to run.** In your process, every import its modules make on pr-rla's thread must resolve inside the files its tree hash covers, its declared dependencies' (never the unhashed `node_modules` or `.git` at the top of either) or the running pr-rla's own code (a resolve hook refuses anything else, such as an undeclared package Node would find in an enclosing `node_modules` or in the plugin's own, or a sibling file of a single-file plugin), and every `pr-rla` it can resolve must be the one running it. The hook covers that thread only: a worker the plugin starts, a process it forks and a `require` it makes with `createRequire` from a path outside its files are not held to it. And it has your files and environment: code that reads a file and runs it is doing what you approved. Approve `trust: full` only for code you would run yourself, and prefer isolated.
- **The child can still see some of the machine.** It can send signals to any process of the same user (`process.kill(pid, 0)` answers whether a process exists, and a real signal such as SIGUSR2 is delivered), and it can learn whether a path outside its grant exists (`fs.realpathSync` returns it, while `existsSync`, `stat` and reads are refused). The permission model covers neither. Checked on Node 22.23.2, 24.20.0 and 26.8.2 (macOS).
- **Echo scrubbing covers the forms above, not every transformation.** A server that echoes a fragment of a secret, or the secret hashed, split or otherwise changed, can hand that to the plugin. The broker only ever sends a secret to an origin you approved.
- **Strong isolation needs the operating system.** For a plugin you do not trust, run pr-rla itself in a container or VM with no ambient credentials. pr-rla ships no sandbox.
- **Install hygiene is yours.** Install plugins with `npm ci --ignore-scripts` (pr-rla plugins need no install scripts; `plugin add` warns when one declares them). npm 11's `allow-scripts` and `min-release-age` help where available.
- **The host needs Node 22.15 or later** (`module.registerHooks`, which links a plugin against pr-rla's own SDK). On an older Node an isolated plugin fails to load with that message; tested only on 22.23.2, 24.20.0 and 26.8.2.

## Trusted time (T17, and the trusted-time review of 2026-11-04)

A registration's or a commitment's time is proven by RFC 3161 tokens from k = 2 independent timestamp-authority operators. A forged token is the cheapest way to fake a prospective audit or to pick the draws after the seed is public, so `verify` decides what counts using only what the verifier brings: the package and the verifier's own flags. Nothing in the audit repo can add trust.

### What verify trusts, and from where

| Evidence | Trusted when | Never from |
|---|---|---|
| An RFC 3161 token | its chain reaches an anchor pinned in the package for that authority (`src/timestamp/trust-bundle.json`), or in a file the verifier passes with `--tsa-trust` (to `verify`, and to `status`, whose certificate needs the same proven times; in CI the `tsa-trust` input, written by whoever owns the CI configuration) | the audit repo |
| A token toward k | it is accepted, and its authority is one the registration names in `timestamping.authorities` | any other authority, even a bundled one (`ignored (not registered)`) |
| A transparency-log entry | its key is pinned in the package (Sigstore's production Rekor v1 and v2 logs, from Sigstore's TUF `trusted_root.json`; the pinned key always wins for those URLs), or the verifier passes it for exactly that log with `verify --log-key <log url>=<pem file>`, and then it counts as the neutral operator `log at <host>`, never as Sigstore | `.pr-rla.yml`'s `transparency_log.public_key_file`, any file in the audit repo, the log URL in the record's unsigned envelope, a `--log-key` given for another log |
| The registration's signing key | the key the registration names inside its signed, time-stamped bytes (`publicKeyPem`, time round B) | the envelope alone: a registration re-signed under another key FAILs check 1 |
| The time a v2 record counts as | its own signed `registeredAt` or `frozenAt`, always | the envelope: dropping `timestamps` FAILs, it never hands the time to a log |

### One signer certificate for every rule

pr-rla finds the one certificate in the token that the CMS signer identifier names (issuer and serial, or subject key identifier; RFC 5652 §5.3), and checks the signature key, ESSCertID, the critical `timeStamping` EKU and the chain on that certificate alone. It refuses a token when no certificate or more than one matches the identifier, when two certificates carry the signer's issuer and serial, or when the library checked the signature under any other key. A test runs 80 signer-identity mutations of the eight authorities' recorded tokens past `openssl ts -verify`: every one OpenSSL rejects, pr-rla rejects too (and pr-rla also rejects the duplicate and appended-twin cases that OpenSSL accepts). The one known difference is that OpenSSL cannot read a subject-key-identifier signer at all; pr-rla accepts a consistent one, and no bundled authority uses that form.

### Chains

Every intermediate must be a CA allowed to issue certificates (critical `cA`, `keyCertSign`, its path length honoured, and an EKU, if it has one, that allows timestamping). DigiCert's and GlobalSign's anchors are general-purpose roots (DigiCert Trusted Root G4, GlobalSign Root R6), and so are SwissSign's and GitHub's; for those four the bundle also pins the operator's TSA issuing CA, and only a signer issued directly by it counts as that operator.

### The limits, stated plainly

- **Three anchors are trust on first use.** Microsoft's (pinned at its intermediate, because its tokens omit the root), SwissSign's and FreeTSA's were taken from the authorities' own responses. Every output that counts one prints `anchor pinned on first use … independent: false`. Confirming them from a second source is a release-checklist item.
- **A pinned issuing CA must be updated when an operator rotates it.** A token signed under a new issuing CA fails until the bundle carries it (NFR21's release diff). Old tokens keep verifying, because issuing CAs are only added.
- **A v1 audit logged to a log whose key is not pinned** is INCOMPLETE (exit 6) unless the verifier passes that log's key with `--log-key <log url>=<pem file>`: its time is in the record's unsigned envelope, and the seed round R is derived from it, so check 3 cannot PASS on it (pass-2 review #2).
- **The parsing library still verifies the signature** (pkijs); pr-rla checks that it did so under the signer certificate's key, byte for byte.

### Unproven is not certified, and draws cannot be ground (time round B, 2026-11-04)

- **One verdict model.** A check is PASS, WARN, FAIL, INCOMPLETE (not established) or SKIP (not run); the audit is FAILED if any check FAILed, INCOMPLETE (exit 6) if any is INCOMPLETE or skipped, else VERIFIED (`src/core/verdict.ts`). A registration or commitment time that k operators do not prove is INCOMPLETE (checks 1 and 2), and so is the seed round derived from it (check 3): whoever wrote the time could have written it after the seed was public. `verify --offline` skips the population rebuild, so it is never VERIFIED.
- **One certificate.** status, verify's line, `audit_list` and the MCP tools print CERTIFIED only when nothing withholds it (`isCertified`); otherwise `target reached · CERTIFICATE WITHHELD (why)`. `sequence.state` is the SPRT's raw state, never the claim. A population below the registered minimum never certifies: draws that exist anyway FAIL check 6.
- **A refused read is not a missing record.** When a provider or ledger ran without its credential (withheld for want of your approval, or not set) and the server refused every read it made with 401, 403 or 404, what it read is not established: check 5 or 7, and status's verdicts, are INCOMPLETE, and the reason names the variable and the `pr-rla plugin approve --env … --origin …` command. A tracker that answers some anonymous reads is readable, so its 404s stay the server's answers (a deleted issue on a public tracker still FAILs).
- **Draws are bound to the registration.** For schema v2, draw *i* is SHA-256(randomness ‖ registrationSha256 ‖ uint64be(*i*)) mod N over the change ids in canonical order (contracts.md §5, "Draws"). Before, the manifest's hash was the binding, and it covers what the freezer chooses (`frozenAt`, the funnel, the limitations): one registration frozen a dozen times before R gave a dozen samples to choose from (time review finding 2). Now freezing again cannot move a draw. What can still move N is SCM state that changes after landing and that pr-rla reads as of the freeze: labels (a `labels:` stratum; `register` notes it and check 2 WARNs), an approval dismissed after the merge, an account renamed. Those are stated limits, not detected.

## Verdict provenance and presence (T7, T16)

A verdict is only as good as the evidence of who recorded it. pr-rla gives every counted verdict a provenance level, prints it on every certificate, and lets a registration require a minimum (FR3.8, FR9).

| Level | What it means | Produced by |
|---|---|---|
| `self-asserted` | `reviewer` and `recordedAt` are whatever the writer typed | the `git-file` ledger: a line with no signature, or one whose signature does not count (another key, another reviewer, another registration, a broken signature) |
| `account` | an SCM account (server-assigned time) or the reviewer's registered signing key did it | the issue ledgers (the label event's actor and `created_at`); a `git-file` line signed by the registered software SSH key of the reviewer it names, or by their registered security key with the user-presence flag clear |
| `presence` | as `account`, and the signature carries the FIDO user-presence (UP) flag from the reviewer's registered security key | a `git-file` line signed by the registered `sk-ssh-ed25519@openssh.com` or `sk-ecdsa-sha2-nistp256@openssh.com` key of the reviewer it names, UP set |

Every certificate prints the level, and prints `presence` as `presence (user-presence flag verified; key hardware not attested)`: `VERDICT PROVENANCE: account (12) · presence (user-presence flag verified; key hardware not attested) (24)`.

### One signature per verdict

A verdict's provenance comes only from its own signature. Each `git-file` line carries `sshsig`: an SSHSIG (OpenSSH `PROTOCOL.sshsig`) in namespace `pr-rla-verdict@v1`, made by `ssh-keygen -Y sign`, over a versioned text (`pr-rla-verdict/v2`) that names the registration's digest, the frozen manifest's digest, the seed (the beacon round and its randomness), the protocol, the draw, the change, the verdict, the reviewer and the time (contracts.md §1, "Per-verdict signatures"). `pr-rla record --sign <key>` makes it; a reviewer who does not want to run pr-rla's process can write the bytes with printf and sign them with ssh-keygen themselves (README, "Signed verdicts").

So one signature is one verdict, on one draw, of one frozen audit. With a security key, one touch signs exactly one verdict: an assistant that appends lines in the reviewer's shell cannot have them all vouched for by the next touch, a line cannot move to another draw or another audit, and rebasing, cherry-picking or amending other people's commits signs nothing that counts. Commit signatures give no provenance at all, and no line is credited to the commit that added it.

Because the bytes name the seed's randomness, a signature cannot be made before the seed is public: the first version of the bytes (`pr-rla-verdict/v1`, before the P4 round) named only the registration, so a reviewer's software key could have signed every (draw, change) pair in advance with a `recordedAt` of its choosing, and a signature stayed valid for any manifest frozen under the same registration. `v1` signatures are refused everywhere (nothing signed under `v1` was released): check 7 says the line is signed over the `v1` bytes and should be signed again.

Under a registration that registers keys and sets `require_signed` or a minimum above `self-asserted`, a line without a valid signature by its reviewer's registered key is **ineligible**: it is ignored, with its reason, as a bot's label is, and the first eligible signed verdict for the change counts. `status`, check 7 and `record` apply the same rule (`countedVerdicts` in `src/core/presence/provenance.ts`), so unsigned lines an assistant appended first can neither stand in for the reviewer's signed verdict nor keep `record --sign` from recording it.

### What the registration fixes

- `verdicts.min_provenance`: the level below which a counted verdict FAILs check 7. The default is `account` with an issue ledger and `self-asserted` with `git-file`.
- `verdicts.allowed_signers`: the reviewers' keys, as lines of OpenSSH's allowed-signers format (`<principal> [namespaces="pr-rla-verdict@v1"] <keytype> <base64 key>`), inline or from an `allowed_signers` file next to the configuration. They are hashed into the signed registration, so rotating a key needs a new registration, which is the point. pr-rla reads a narrower form than `ssh-keygen`: one principal per line, an exact name; no two principals equal ignoring case; no key under two principals; the only option is `namespaces`, which must admit `pr-rla-verdict@v1`.
- `verdicts.reviewers`: whose verdicts count at all (logins and `id:<account id>`), as before; it is no longer where keys go.
- `verdicts.require_signed`, from the `git-file` option `require_signed: true`: every counted verdict must carry a valid signature by the registered key of the reviewer it names. Only the built-in `git-file` ledger can be registered with it.
- `ledgerPath` (the P4 round): the built-in `git-file` ledger's path from the audit repository's toplevel, as the configuration names it (`<audit_dir>/<window>/<file>`), lexical and normalised. Check 7 FAILs when the ledger it walks is anywhere else (below).

`register` refuses rules no verdict could meet (`account` with `git-file` and no keys, `presence` with no registered security key, `require_signed` with no keys or another ledger, keys with any ledger but `git-file`), and warns when keys are registered but neither `require_signed` nor a minimum above `self-asserted` is set, since unsigned verdicts would then still count.

### How pr-rla checks a signed verdict

For each line, the core's PresenceVerifier (`src/core/presence/`, pure: node:crypto only, no file, process or network access):
1. rebuilds the signed bytes from the line's fields and **this** audit: the registration's digest (a line naming another registration is refused), and the manifest digest and the seed that checks 2, 4 and 6 have verified (`status` and `record` read them from `manifest.json` and `draws.json`);
2. parses the SSHSIG and checks the `SSHSIG` preamble, version 1, an empty reserved field, namespace `pr-rla-verdict@v1` and a `sha256` or `sha512` message hash;
3. requires the signing key to be a registered key, byte for byte, admitting the namespace, and the line's `reviewer` to be that key's principal, exactly (as `ssh-keygen -Y verify -I` matches);
4. verifies the signature in TypeScript: Ed25519, ECDSA P-256, P-384 and P-521, RSA (rsa-sha2-256 or rsa-sha2-512, 2048 bits or more, an odd exponent above 1; SHA-1 `ssh-rsa` is refused), and for the FIDO types the authenticator's signed data, `SHA256(application) ‖ flags ‖ counter ‖ SHA256(signed data)` (OpenSSH `PROTOCOL.u2f`), with an application that starts with `ssh:`; small-order Ed25519 keys and WebAuthn signatures are refused;
5. for a security key, reads the UP flag (bit `0x01`) itself.

A level a line writes about itself never counts. A ledger cannot raise a verdict above what it can attest: `presence` comes only from this check of a `git-file` line, the issue ledgers top out at `account` (a label event carries no presence evidence), and an external ledger is never counted above `account`. Signatures count only when the ledger `verify` loaded is the registered one: check 7 FAILs when its name, source, files (`integrity`) or options differ from the registration's `plugins.ledger`, and takes the ceiling from the registered identity. Check 7 WARNs on an unreadable, invalid or foreign signature, an unlisted key, a signer who is not the reviewer the line names, and a security key whose signature counter goes down.

### The ledger's history

Signed lines can still be deleted, so `verify` walks the history of `verdicts.jsonl` itself: every commit reachable from HEAD through the parents its raw commit object names (no `git log` history simplification, no rename following), each object read with `git cat-file --batch` and checked to hash to its name. Every version of the file must extend the version in each of its parents, so a removal, a relabel or a rewrite anywhere, on any merged branch, FAILs. git runs through one guard (`src/io/git-safe.ts`): every inherited `GIT_*` variable dropped, no lazy fetch, no optional locks, no automatic gc or maintenance, no climbing above the repository, no replace refs, no commit-graph, no fsmonitor, and no textconv (the walk reads blobs, never diffs).

The walk reads the path the registration records, and only that path (the P4 round, after a second review). The ledger's path is computed from the repository's toplevel as the configuration spells it, never through `realpath`, and every directory on it must exist on disk under exactly its name in its parent's listing and not be a symbolic link: otherwise the walk would follow a link (`audit/2026-q3 -> real`) or a case-folding filesystem (`Verdicts.jsonl` for `verdicts.jsonl`) to a file with another history. Check 7 FAILs on a symbolic link or another spelling, and when the walked path differs from the registered `ledgerPath` (an audit copied to another `audit_dir`); a registration without the field (made before it existed, only test fixtures) WARNs that the location is not bound. `record` refuses to write through such a path. With HEAD present and the registration beside the ledger committed, a ledger file with verdicts that has never been committed at its path FAILs, since its lines have no tamper trail where verify reads them. `status` runs the same walk and path rule, so it never prints CERTIFIED where verify would FAIL check 7 for a `git-file` ledger; since P1 it runs check 7's whole gate (`src/core/ledger-gate.ts`), for every ledger.

The walk streams: each raw object is parsed as git writes it and dropped, keeping per commit only its tree and parents and per tree only the entry on the path. 200,000 commits took 274 MB peak RSS (921 MB before), and 30,000 commits with a 65 KB root tree 141 MB (2,043 MB before).

A shallow clone, a repository with a grafts file or a hand-written `shallow` file, and a partial clone are refused before anything is read: check 7 FAILs and says to verify in a full clone. In a shallow clone the history before the cut is not there, so a verdict removed before it could not be seen; earlier versions of this page said such lines "lose their level", which was wrong (they took the boundary commit's level). A missing object is reported as missing, never as a deletion, and is never fetched.

### The limits, stated plainly

- **`presence` does not prove a person touched hardware (T16).** A software-emulated authenticator sets the user-presence flag as easily as a hardware key does. So `presence` relies on each reviewer having registered a hardware-backed security key; pr-rla does not check that a registered key is hardware-backed (key hardware not attested). Closing this would need FIDO attestation at registration (`ssh-keygen -O write-attestation`, verified against the authenticator vendors' roots); it is not built.
- **Tested with software keys only (D7).** The `-sk` signatures in the test suite come from OpenSSH's own sk-dummy test middleware and from a software-emulated authenticator in the tests; no hardware key has been used, and no doc or certificate claims hardware-verified presence.
- **Don't register your everyday signing key.** Register a key you keep for verdicts, with `namespaces="pr-rla-verdict@v1"`. A touch request from a key you use only for verdicts at least tells you that some verdict is being signed, though not which one (next point); one from the key that also signs your commits and SSH logins is easy to grant without looking. And anyone who can use a registered software key (an assistant in your shell, a process reading your key file) can sign verdicts as you at `account`.
- **A touch is presence for one signature, not a review.** The authenticator does not show what it signs, so a reviewer could be talked into touching for a verdict they did not make. Even with a hardware-backed key, which pr-rla does not check (T16), `presence` rules out "no human at all" for that one verdict, not "no review".
- **`ssh-keygen -Y verify` and `git verify-commit` do not enforce the presence flag.** OpenSSH 10.3p1 accepts a security-key signature whose UP flag is clear, and neither `-Y verify` nor the allowed-signers format has an option that requires it (checked 2026-11-04; `test/presence-oracle.test.ts`). pr-rla checks the flag itself; verifying with ssh-keygen alone would accept a touch-less signature. ssh-keygen also accepts things pr-rla refuses on purpose: a small-order Ed25519 key whose one "signature" verifies every message, RSA keys of 1024 to 2047 bits, a non-empty reserved field, and WebAuthn signatures.
- **The counter is a WARN, never a FAIL.** Authenticators differ: some report 0, OpenSSH's test middleware a constant. A counter that goes down for one key can mean a cloned key, so it is reported.
- **A signature binds the verdict to the reviewer's key, not to a time.** `recordedAt` is signed, but it is still the signer's own clock.
- **The walk sees the history it is given.** It catches a removal or rewrite anywhere in the history reachable from HEAD. A history rewritten wholesale (a new root, force-pushed, with the signed lines copied over without the ones the rewriter dislikes) is not visible from the repository alone: protect the default branch and keep the audit repository where force-pushes are refused, and compare with a clone taken earlier.
- **git and ssh-keygen are found on PATH, never in the audit repository.** pr-rla resolves each to an absolute path from the absolute entries of PATH once, and runs that file (`src/io/executables.ts`): on Windows a bare `git` would otherwise be looked up in the audit repository first, where a committed `git.exe` could run, and on any platform a relative PATH entry (`.`) is the working directory. Windows is untested.
- **SHA-1 repositories hash-check objects without collision detection.** pr-rla recomputes each object's SHA-1 itself; it does not run git's collision detection over it, so a repository whose objects were built with a SHA-1 collision (chosen-prefix collisions are practical) could pass the check with two contents under one name. A SHA-256 repository (`git init --object-format=sha256`) does not have this exposure; the per-verdict signatures (SHA-256 or SHA-512 message hashes) do not depend on git's hash either way.

## The registered plugins and the draw → issue mapping (P1)

Two holes let an auditee change what an audit counts after registering it. Both are closed by binding to records the auditee signed and the authorities time-stamped before the verdicts:

- **Another plugin than the registered one.** Registration signs `plugins.provider` and `plugins.ledger`. Before P1 the commands loaded whatever `.pr-rla.yml` named: a provider swapped for a forged `json-file` export, or re-locked so that it left a change out, rebuilt a matching population, and verify printed a WARN at most (between two built-ins, nothing). Now every command runs only the registered plugin (`src/core/plugin-binding.ts`), and verify FAILs check 5 or 7 on any difference, the manifest's own `provider` included.
- **Re-pointing draws at other issues.** `ledger-index.json` maps each draw to the issue its verdict is read from. It is the auditee's file, and so are the issue bodies whose markers name the draw: swapping a failing draw's issue with a late passing one, with the two bodies swapped too and `draws.json` rehashed, turned a three-FAIL audit into CERTIFIED with 7/7 PASS (pass-2 review #1). Checkpoints taken earlier showed it, but checkpoints can be removed and taken again. Now `sample` signs the index it leaves and has the registered authorities time-stamp it (`ledger-publication.json`), before any reviewer can label the issues, and every later publication must extend the previous one. Check 7 FAILs an index that is not an extension of the latest publication; a verdict read from an issue no proven publication lists; and a counted verdict older than the first proven publication that lists its issue, which is what a publication remade after the fact looks like. Issue numbers must also rise with the draws (pr-rla opens issues in draw order), so a permutation breaks the index even before it meets the publication. `foreignIssues`, which turned the marker check off, is no longer an index field: an index carrying it FAILs, and recorded test timelines use the test-only ledger option `foreign_issues`, which check 7 also FAILs. The GitHub ledger names issues by their numeric id. The requirement is keyed on the signed registration (schema v2, a ledger that publishes draws), so a missing file FAILs too.
- **The Jira example** applies the same publication record, and checks what the core cannot: each read asks Jira what the index's two option ids are now (the index's option ids were taken on trust, so swapping them inverted every verdict, pass-2 review #3); a changelog entry whose id and value disagree FAILs; and an issue's summary, its marker, must name its draw and never have been edited (Jira, unlike GitHub, records summary edits in the issue's changelog).

What remains: with no authority registered, nothing is time-stamped, so the publication records rest on the auditee's own signature and clock (check 7 WARNs `TIMESTAMP NOT TAMPER-PROOF`). A publication short of tokens counts for nothing: `sample` exits 5 and says to publish again before anyone labels the new issues, and a verdict that only such a publication binds leaves check 7 INCOMPLETE (not established), never PASS. A token that fails a rule FAILs, as the registration's does.

## Org-pooled audits (U8)

A pooled audit adds one more thing the auditee controls: which repositories the pool holds. The rule (an owner, globs, the archived, fork and visibility flags) is registered before the seed, but the attributes it filters on belong to the repositories' owners, who can change them at any time. The principle the U8 fix round applies: nothing the auditee controls after registration may silently remove changes from the population, and nothing the verifier cannot check prints `VERIFIED`. The P3 round adds: the frozen head is proved from what the SCM records when the branch moves, never from commit dates or the shape of the history, which the pusher sets.

### What pr-rla does

1. **The resolution is registered, with what its token could see.** `register` signs the repos a rule matches, by the SCM's stable repository id, and the token's proof per visibility (`registeredVisibility`). Freeze includes every registered repo that still exists, whatever its archive state, visibility, name or owner by then; one found gone is recorded with the repo-level probe's evidence. Check 2 FAILs a rule registration without registered repos and a manifest that drops one, offline; check 5 is INCOMPLETE for each private or internal visibility the registering token could not prove it saw in full, and `register` warns about it.
2. **The freeze's whole listing is recorded.** The manifest holds every repository the token listed under the owner, with its flags and the rule clauses that excluded it, the identity that listed them and, per visibility, the count and whether the listing was provably complete. Check 2 recomputes each exclusion from the recorded attributes.
3. **verify lists again and compares, by id.** A registered repo outside the pool FAILs, as does one the freeze's own listing says the rule matched; a rename is matched by id. A repo the rule matches now that the freeze's listing did not show, with window changes, is INCOMPLETE: it may be a transfer in. A repo excluded at freeze by its archive state alone, with window changes, FAILs in a prospective audit or when it was created after the registration (an archived repository is read-only, so it was archived after them); one excluded by its name or visibility and created after the registration is INCOMPLETE; other attribute exclusions with window changes are one WARN line with the counts.
4. **verify must show it sees what it checks.** For private and internal repositories it needs the provider's proof that the token sees every one. Without it check 5 is INCOMPLETE, so a pruned private repo can never pass unseen. On GitHub the proof is an org owner (`/user/memberships/orgs/{org}`: `role: admin`, `state: active`) with a classic token holding the `repo` scope (`X-OAuth-Scopes`), the token's own user account, or a GitHub App installation whose `GET /installation/repositories` says `repository_selection: "all"` on the owner. When GitHub sends the org's `total_private_repos`, the listing must hold at least that many private and internal repositories; an OAuth App token (`gho_`), which an org's OAuth App access restrictions can limit to public repositories without saying so, proves nothing without that count. That is sufficient because GitHub shows an org owner every repository of the org and a classic token is not limited to selected repositories, and it is necessary because a member sees only the private repositories they were granted and a fine-grained token or an app on selected repositories can be limited without any API saying so.
5. **The frozen head is held to the push log.** verify rebuilds each repo from the head the manifest records, lists the window from the branch's current head, and reads the branch's push log (GitHub's repository activity, GitLab's push events): updates the SCM records, with their times, as the branch moves. A head the log shows was not the branch's tip at any instant from the manifest's as-of time until R published FAILs. A head it proves makes a window commit the head does not reach legitimate (it reached the branch after the window closed, FR7.2); after an update the SCM does not call a fast-forward, the branch's tip at the window's close must be an ancestor of the frozen head, or the changes it held that the head lacks FAIL. With no usable log such a commit is INCOMPLETE, never PASS and never FAIL. A pull request merged in the window whose merge commit the frozen head does not reach always FAILs (the stopgap, which every built-in reports from its own ancestry answer).
6. **Gone is decided by one probe.** A repository counts as gone only when its own metadata answers 404 (or a 403 the provider documents as hiding a repository). A 404 on a commit of a repository that exists FAILs ("frozen head not found"); a rate limit is never "gone". A gone or unreadable repository makes verify INCOMPLETE (exit 6), never VERIFIED.

### The limits, stated plainly

- **What a retrospective pooled audit cannot detect: attribute changes made before registration.** A repository archived, made private or renamed out of the rule during the window but before a retrospective registration is not among the registered repos. verify WARNs with its change count, and cannot say when the change was made. A prospective registration (before the window opens) closes this: every repository the rule matched before the window stays in the pool.
- **Direct pushes are dated by their committer date, which the pusher sets.** A direct push dated outside the window is outside the population (the window is still applied to the date; push times only place a commit relative to the frozen head). Where the SCM keeps no push log pr-rla can read (Bitbucket Cloud and Data Center, a token that cannot read it, a log past its retention), a moved head is INCOMPLETE wherever a window commit is not reachable from it.
- **The push log is the SCM's, and so is its retention.** GitHub documents none (on 2026-11-04 the oldest updates it served were from 2023-03-07 for a repository older than that); GitLab removes events after three years, does not record whether a push was forced, and records a push of many refs at once without its commits. The push log, like everything verify reads, comes from the provider and its host, which the audit names; a provider that lied about it is the provider-trust question of the plugin section above.
- **Force pushes inside the window** remove commits from the branch; those commits are not in the population. verify reports how many such updates the log shows.
- **A hidden repository is no repository.** Without the provider's proof of complete visibility, verify cannot know that a repository it cannot see exists. That is why the answer is INCOMPLETE rather than a pass.
- **The registering token defines the registered repos.** A repository the registering token could not see is not registered; if the rule matches it at freeze it joins the pool, and a verifier who can see it FAILs a manifest without it, but nothing holds it in the pool against a later attribute change. That is why a registration whose token could not prove it saw a visibility in full leaves check 5 INCOMPLETE for it. Register with a token that can see the whole owner.
- **Transfers.** No built-in provider can tell a repository transferred in after freeze from one the freeze's listing left out, so such a repo with window changes is INCOMPLETE, not FAIL.


## Assistants, `draw-context` and the MCP server (T7, FR3.2, FR3.9)

An assistant can read an audit through `pr-rla draw-context` or the MCP server, `pr-rla-mcp` ([`packages/pr-rla-mcp`](../packages/pr-rla-mcp)). The asset at stake is the reviewer's verdict authority: a verdict must be a person's.

### The verdict-authority guarantee

> pr-rla's MCP tools and its review skill never record, edit or remove a verdict, never issue draws and never submit to a public log. A read-only mode enforces this, and a test checks every tool.
>
> pr-rla cannot stop an assistant that has your shell and your credentials from acting as you. Client permission rules and hooks are not a security boundary, and some clients let an AI approve tool calls.
>
> What pr-rla can do is make such verdicts not count:
> - give the assistant a read-only token;
> - record verdicts where the assistant cannot, in the SCM web UI;
> - register the reviewers whose verdicts count.
>
> `verify` then reports any verdict below the registered provenance level. Signed verdicts with a security key (`presence`) are supported, but in this release they have been tested only with software keys. pr-rla does not check that a registered key is hardware-backed.

### How it is built, in three tiers

Only the first two are guarantees; the third is a speed bump.

1. **pr-rla's own surfaces never write** (enforced, tested).
   - The MCP server imports only `pr-rla/api/read`, whose functions run in read-only mode: the fetch broker refuses every request that is not a read (`GET`, `HEAD`, a GraphQL query) before it is sent, no recorder is installed, and a ledger is opened with its read methods only. The write functions (`register`, `freeze`, `sample`, `record`, `checkpoint`, `init`, `plugin add` and `lock`) live in `src/api/write/`, which the subpath never imports (`test/api-read-boundary.test.ts` walks the import graph), and each refuses a read-only context with `READ_ONLY_VIOLATION` before it starts.
   - `packages/pr-rla-mcp/test/mcp-readonly.test.mjs` starts the server over stdio with the MCP SDK's own client, under Node's permission model with no fs-write grant and a guard that reports any write call, and calls every tool with valid and hostile inputs (path traversal, symlinks out of the roots, a config naming files outside them, draws past the cap, oversized and malformed arguments, a change whose text tries to give orders). The audit directories' tree hashes, `.git` included, are unchanged; the server attempted no write; the mock SCM saw only reads.
   - There is no tool that records, issues draws or submits, and no elicitation: the server never asks the client a question, so no auto-answered dialog can stand in for a person.
2. **With the recommended setup, a verdict from an assistant does not count** (enforced by the ledger and check 7, not by the client).
   - **Separate credentials.** The assistant's MCP configuration gets a read-only token. The ledger-write credential lives only where the person acts: the SCM's web UI for issue ledgers, or their own terminal and signing key for `git-file`.
   - **Registered reviewers.** `verdicts.reviewers` lists the accounts or signing keys whose verdicts count. Agent and bot accounts are never on it; a label event from an unlisted account is ignored, with a check-7 detail.
   - **App-applied labels.** On GitHub, an event with `performed_via_github_app` set is not counted by default.
   - **Presence attestation** (U9: the user-presence flag verified; key hardware not attested) is designed to be the tier that holds even then. In this release it is verified with software keys only, so pr-rla does not claim it proves a human touched a hardware key.
3. **Client-side guards** (best effort): the guard hook in the Claude Code plugin, and the same file in Codex and Cursor, with the `review-draw` skill's rules (U6, [`docs/assistants/guard.md`](assistants/guard.md)). As far as it can read a command or a tool call, the guard blocks verdict writes, verdict labels, signing, consent and edits to audit records from the assistant. Client permission rules and hooks are not a security boundary.

### Untrusted text from the change (FR3.9)

A change's title, description, patches, file names and CI check names are written by whoever authored the change, often an agent, and may hold instructions aimed at the assistant. So may its author and merger names (a direct push's author is free text from the commit), its labels, a verdict's reviewer and note (the ledger's), a ledger's error, and the tracker's issue URL and label names. The core builds the draw context with all of it in an `untrusted` object, and its text rendering puts it between `<<<UNTRUSTED-CHANGE-CONTENT <id>>>>` and `<<<END <id>>>`, with 128 fresh random bits as the id on every call, so the text cannot close the fence by guessing it. Outside the fence are only pr-rla's own words and counts, the frozen manifest's identifiers and the registered protocol; a protocol whose hash is not the registered one gets a FAIL line and no checklist. The MCP server passes the core's fence through and adds none of its own; its instructions to the client say that text inside the fence, and an error's `untrusted` field, are data. A read call's error is pr-rla's sentence: what an SCM response, a ledger or a plugin said goes to `untrusted` (a server that echoes a request or an instruction in its error body never speaks in pr-rla's voice), and a plugin cannot claim pr-rla's "no description" note. The same holds for the failures `verify` records instead of throwing (a ledger's in check 7, a beacon relay's in check 4): in read-only mode the check's line is pr-rla's and points to `untrusted.errors[i]`; the CLI, a person's own terminal, quotes them in place with their control characters escaped. This lowers the risk of prompt injection; it cannot rule it out, which is a second reason the verdict stays with the person.

Every text rendering escapes control characters it did not write: C0 controls other than newline and tab, DEL, C1, and the bidirectional controls (Trojan Source), as `\uXXXX`. That covers the draw context's text and every line the CLI prints (stdout and stderr, `--json` included, where `\uXXXX` is a valid escape), so a patch cannot move the cursor and rewrite pr-rla's verdict or protocol lines, or hide the fence's close.

### A change cannot hide its own files

Under the registration's `exclude_generated`, the draw context drops `linguist-generated` files by name. Generated status comes from the `.gitattributes` of the change's base commit and of its landed commit, and a file is dropped only when both mark it (for a rename or copy, its old path too); a `.gitattributes` itself is never generated; and when the change touches any `.gitattributes`, or its file list is truncated, nothing is dropped, with a note outside the fence. The rules are git's own (`src/core/generated.ts`, checked against `git check-attr` with nested files, macros and a seeded fuzz), matched by a linear-time automaton under a work budget, so a hostile pattern cannot stall the server; whatever cannot be decided is shown.

### What the MCP server can reach

- **Only its roots.** `--root <dir>` (repeatable; the working directory by default). A tool's `dir`, and every file the audit API opens for it (the config, the audit directory, the protocol, a json-file export, the transparency-log key, every record and window file, the ledger's file, checkpoints and their history, the ledger index), must resolve inside a root by `realpath`, checked as the file is opened and on the path actually opened (`O_NOFOLLOW`), or the tool returns `ROOT_ESCAPE`, naming what was refused but not where it resolves. No error quotes a file's contents (a JSON or YAML parser's message would). git, run to read the git-file ledger's history, never looks above the roots (`GIT_CEILING_DIRECTORIES`), a `.git` file pointing out of them is refused before git reads it, and git runs with no lazy fetch (a partial clone's missing object is reported, not fetched with your git credentials), no optional locks and no automatic housekeeping. The server does not depend on the client to supply roots. Residual: a concurrent writer that can rename directories inside a root during a call could race the check; that writer already controls the audit.
- **Memory, not disk.** Jobs (a call still running after 25 s), finished results for 600 s, and finished freeze previews for 600 s live in memory and die with the process. At most four long calls run at once; a result over 8 MiB is refused; finished jobs are bounded to 32 and 32 MiB, the oldest dropped first. Each long call stops at its deadline (`LONG_CALL_DEADLINE_MS`, 1 h 30 s: the longest default rate-budget window plus one request's timeout), when the client cancels it before the hand-off, or when the client goes away: its requests, waits and plugin hosts end with it.
- **Annotations are hints.** Every tool carries `readOnlyHint: true`, and some clients auto-approve such tools. That is acceptable only because the tools really are read-only, which the first tier enforces.
- **No `trust: full` plugin, and no repo-chosen credential.** Read-only mode (the MCP server, `pr-rla/api/read`) refuses to load a `trust: full` plugin (`FULL_TRUST_REFUSED`): only built-ins and isolated plugins run there, and an isolated one cannot write files. The audit repo's `.pr-rla.yml` and `pr-rla.lock.json` are not the operator's, so in read-only mode they cannot choose which of the operator's secrets is used or where it goes: a built-in sees only its documented default token variables (`GITHUB_TOKEN`, `GH_TOKEN`, `GITLAB_TOKEN`, `BITBUCKET_TOKEN`, `BITBUCKET_USERNAME`), as placeholders the fetch broker swaps only on its default https origin (`api.github.com`, `gitlab.com`, `api.bitbucket.org`); a `token_env`, a non-default base URL (GitHub Enterprise Server, GitLab self-managed, Bitbucket Data Center), or a lock entry's credential grant needs the operator's consent: the same approvals file the CLI asks ("If you verify someone else's audit" above; `pr-rla plugin approve`). Read-only mode takes only what is approved there, never `--accept-lock-grants` or `PR_RLA_ACCEPT_LOCK_GRANTS`; anything else is withheld, the call runs without it, and the server's log names the approval command. A secret is never sent over `http:`. Nothing else of the environment reaches a plugin. Residual: a config can still point a built-in at another host for anonymous GET requests (an internal address, say); the responses only reach the caller as parsed fields or, in an error, as untrusted text. Start the server with `--plugins builtin-only` (or `PR_RLA_PLUGINS=builtin-only`) to refuse external plugins altogether.
